1. Introduction

1.1 Objectif du document

Ce document décrit les exigences fonctionnelles et non fonctionnelles du système de gestion opérationnelle de la collecte des déchets, conçu pour un contexte de type HYSACAM (Yaoundé, Douala, Cameroun). Il sert de référence pour le développement, les tests et la maintenance.

1.2 Périmètre du produit

Le système couvre :

  • Un tableau de bord opérationnel (collecte du jour, indicateurs, alertes).
  • La planification et le suivi des tournées de collecte (affectation chauffeur, camion, unité, date, statut, avancement).
  • La gestion des chauffeurs, camions (bennes), unités opérationnelles et sites (centres de transfert).
  • Une interface web responsive et une API REST pour la persistance (MongoDB ou localStorage en mode déconnecté).

Hors périmètre dans cette version : authentification multi-utilisateurs, facturation, géolocalisation temps réel, application mobile dédiée.

2. Description générale

2.1 Perspective du produit

L’application est une application web monopage (SPA) côté client (React, Vite) et un serveur API (Node.js, Express) optionnel. Les données peuvent être stockées soit en base MongoDB (mode connecté), soit en localStorage (mode déconnecté ou démo). Le déploiement cible frontend (Netlify) et backend (Railway), avec MongoDB Atlas pour la base de données.

2.2 Fonctions principales

  • Tableau de bord : synthèse du jour (nombre de tournées, terminées, ponctualité, en retard), liste des sites à évacuer (capacité ≥ seuil), liste des tournées en retard.
  • Tournées : création, modification, suppression ; filtrage par date ; affectation chauffeur, camion, unité ; statut (À l’heure, En retard, Critique) et pourcentage d’avancement.
  • Chauffeurs, camions, unités, sites : CRUD complet (liste, ajout, modification, suppression).
  • Paramètres : page dédiée (accessible depuis le menu utilisateur).
  • API REST : ressources /api/chauffeurs, /api/camions, /api/unites, /api/sites, /api/tournees (GET, POST, PUT, DELETE) et /api/health.

2.3 Classes d’utilisateurs

ClasseDescription
Responsable opérationsConsulte le tableau de bord, les alertes, planifie et suit les tournées.
Administrateur de donnéesGère les chauffeurs, camions, unités et sites (CRUD).
Utilisateur finalAccède à l’ensemble des écrans ; pas de distinction de rôles dans la version actuelle.

2.4 Contraintes

  • Interface en français.
  • Compatibilité navigateurs modernes (Chrome, Firefox, Safari, Edge).
  • Responsive (mobile, tablette, bureau).
  • Backend optionnel : l’application doit fonctionner sans API (données en localStorage).

4. Interfaces externes

4.1 Interface utilisateur

  • Application web responsive (HTML5, CSS3, JavaScript).
  • Framework UI : React 18, React Router 7, Vite 6.
  • Styles : Tailwind CSS, thème « recyclage » (blanc, noir, vert, rouge, bleu) avec variables CSS (--color-primary, --color-success, --color-error, etc.).
  • Composants réutilisables : Header (navigation, menu utilisateur), Button, Input, Select, Checkbox, ApiStatusBanner, MetricCard.
  • Icônes : lucide-react.

4.2 API REST (backend)

Base URL configurable (ex. https://waste-track-production.up.railway.app). Toutes les réponses JSON en UTF-8. CORS autorisé pour toute origine.

4.3 Base de données

MongoDB (Atlas ou instance locale). Collections : chauffeurs, camions, unites, sites, tournees. Identifiants : ObjectId exposés en tant que id (chaîne) dans l’API.

5. Modèle de données

5.1 Entités

EntitéChamps
Chauffeurid (UUID/ObjectId), nom (string), telephone (string)
Camionid, numero (string), capacite (string, ex. "5 t")
Uniteid, nom (string), secteur (string)
Siteid, name (string), capacity (number 0–100), status (string)
Tourneeid, name, chauffeurId (réf.), camionId (réf.), uniteId (réf.), status, completion (0–100), secteur, datePrevue (ISO date)

5.2 Relations

Une tournée référence optionnellement un chauffeur, un camion et une unité (identifiants). Aucune contrainte d’intégrité référentielle côté base dans la version actuelle (suppression d’un chauffeur n’efface pas les tournées ; les références peuvent devenir orphelines).

6. Exigences non fonctionnelles

6.1 Performance

  • Chargement initial de l’application : cible < 5 s sur connexion moyenne.
  • Réponse API : cible < 2 s pour les requêtes CRUD.

6.2 Sécurité

  • Pas d’authentification dans cette version ; l’accès est contrôlé par l’hébergeur (Netlify/Railway) et la non-exposition des secrets (variables d’environnement).
  • MONGODB_URI et tokens ne doivent pas être versionnés.

6.3 Disponibilité

Dépend des plateformes (Netlify, Railway, MongoDB Atlas). Objectif : disponibilité standard des services cloud.

6.4 Maintenabilité

Code modulaire (composants React, contexte DataContext, client API dédié), documentation (README, DEPLOYMENT, SRS).
